# Identity and Access

Authentication answers who the caller is. Authorization answers what that caller may do to this specific
object. Most severe access defects come from a system that answers the first question well and never asks the
second.

## Authorization

Broken access control is the class that static analysis finds least and that costs the most. Review it by
object, not by route.

For every handler, ask which object the request names, who owns that object, and where the code compares the
two. If the comparison is missing, the identifier in the request is an insecure direct object reference,
whatever it is called. An unguessable identifier is not an authorization check; it is a delay.

Check the enforcement point. Authorization applied in the presentation layer, in a client, or by hiding a
control is not enforcement. Prefer a single choke point that the data access layer cannot be used without,
such as a scoped query that always filters by the caller's tenant, over a check repeated in every handler and
forgotten in one.

Look for these specific gaps:

- a route added to a controller whose sibling routes are guarded, but which the guard's list does not name;
- a check on the resource the request names, while the operation actually reaches a nested or related object;
- a bulk, batch, export, or search endpoint that authorizes the request once and then returns objects across
  owners;
- an administrative or internal endpoint reachable from the public router because the only separation is the
  path prefix;
- a state transition allowed out of order, so a record moves to an approved state without passing the check
  that grants it;
- a role or permission read from the request, a JWT claim the server never verified, or a header a proxy is
  assumed to strip;
- an ownership check that runs before a value is re-read or re-parsed, so the checked object and the used
  object differ; and
- functions that a lower-privileged role can call directly even though the interface does not offer them.

In a multi-tenant system, ask what happens when the tenant identifier is absent, empty, null, wildcard, or
belongs to another tenant. Each of those should fail closed and usually one of them does not.

## Authentication

Credential storage is settled. Passwords need a memory-hard or deliberately slow password hash with a per-user
salt and current parameters. A general-purpose hash, with or without a salt, is a defect. Verification must be
constant-time, which the password-hash library already provides and a manual comparison does not.

Beyond storage, check:

- a comparison of any secret, token, or signature that short-circuits on the first differing byte;
- registration, login, and password reset responses that differ enough to enumerate accounts, including by
  timing;
- a password reset token that is guessable, long-lived, reusable, or not invalidated on use and on password
  change;
- credential-stuffing exposure, which needs rate limiting per account and per source plus a lockout or delay
  strategy that itself cannot be used to lock a victim out;
- a second factor that the flow allows the client to declare satisfied, or that a legacy endpoint bypasses;
- default, seeded, or shipped accounts that remain enabled; and
- a fallback path, such as a legacy API, a mobile endpoint, or a service account, that authenticates more
  weakly than the primary one.

## Sessions and Tokens

Session identifiers must be generated by a cryptographically secure source, rotated on privilege change and
at login, invalidated fully on logout, and given both an idle and an absolute lifetime. A logout that only
clears client state leaves a valid credential in the attacker's hands.

For cookies, check `HttpOnly`, `SameSite`, the `Secure` flag in production, and a scope that does not widen
the cookie to sibling subdomains that other teams control.

For signed tokens, the recurring defects are structural:

- accepting the algorithm the token itself declares, which permits algorithm confusion and the none algorithm;
- verifying the signature but not the issuer, the audience, or the expiry;
- treating a token as a session, so revocation is impossible before expiry;
- storing a token where script can read it, then relying on that token for authorization; and
- refresh tokens that neither rotate nor detect reuse.

## Cross-Site Request Forgery

CSRF applies to any state-changing request whose authorization is carried automatically by the browser,
whether by cookie, by basic authentication, or by client certificate. A request authorized by an explicit
header that script must set is not vulnerable, which is why token-header APIs generally are not.

Where cookies do carry the session, check that state-changing requests use a synchronizer or double-submit
token bound to the session, that `SameSite` is set as defence in depth rather than as the only control, and
that the origin or referrer check, if present, treats a missing header as a failure. Confirm that no
state-changing action is reachable by `GET`, including logout, and that a login flow cannot be forged to fix
the victim's session to the attacker's account.

For browser-invoked APIs, review the CORS configuration as part of this: reflecting the request origin while
allowing credentials is equivalent to allowing every origin, and a null origin allowance is reachable from a
sandboxed frame.

## What to Verify Before Reporting

An access-control finding is worth a maintainer's time only when you can name the caller, the object, and the
missing comparison. Trace the request to the line where the check should be and confirm no middleware,
decorator, policy layer, or scoped query already applies it. If you cannot rule that out, the item belongs
under Needs Verification with the exact question.
