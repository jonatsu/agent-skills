# Setup and onboarding

## Mental model

Setup stages usually flow: wrap → onboard → setup → bootstrap → init. Names
differ by entrypoint, but intent stays stable: install binary, connect
shell/editor/MCP, generate safe guidance, and verify integrations.

`install` is an alias for `setup`, not a separate stage — running both does the
same work twice, and each run is a writer command (see "Setup gotchas").

## Fresh install

1. Install or update the `lean-ctx` binary using upstream-supported method.
2. Default to no environment mutation first: manual MCP config or
   `lean-ctx init --agent <tool>`.
3. Ask whether shell-hook or RC-file edits are also wanted before using
   onboarding/setup/global init flows.
4. Accept rules/instruction changes only when user explicitly wants them.
5. Restart or reload editor/MCP host if tool-list registration changed.
6. Run `lean-ctx status` and `lean-ctx doctor`.

## Onboarding outputs

- CLI and MCP availability checks.
- Optional shell hook edits.
- Optional editor MCP config snippets.
- Optional rules/instruction files.
- Backup files such as `*.lean-ctx.bak` before RC edits.

## Which CLI forms are safe to run

This table transcribes CLI behavior, which this skill normally refuses to carry
because `--help` answers it live. The exception is that here the live source is
not merely unhelpful but actively harmful: `--help` on `init` performs an
install, so the usual "ask the tool" route is the trap itself.

Verified against lean-ctx 3.9.19, each run with `HOME` and `XDG_CONFIG_HOME`
redirected to a throwaway directory under sha256 guards over the real shell RC
files and config dir. "Writes" is what appeared in the sandbox.

| Command | stdout | writes |
|---|---|---|
| `init <shell> --style=dropin` | that shell's hook | nothing |
| `config schema` | the JSON schema | nothing |
| `doctor` (no `--fix`), `status` | diagnostics | nothing |
| `init --global --style=dropin` | a progress report | `~/.bashrc`, `~/.bash_profile`, `env.sh`, `shell-hook.bash` |
| `init --help` | a progress report | the same four |

The distinguishing argument is the SHELL NAME positional with no `--global`.
Dropping the shell name turns a print into an install.

All four shell names were exercised, not just `bash`: `bash`, `zsh`, `fish` and
`powershell` each printed their own hook and wrote nothing. Note their header
lines differ — `bash`/`zsh`/`fish` say "smart shell mode (track-by-default)"
while `powershell` says "transparent CLI compression (95+ patterns)" — so a
header string is NOT a staleness signal; it identifies the variant.

NOT verified: `wrap`, `onboard`, `setup`, `install`, `update`, `doctor --fix`,
`skill`. Treat every one as a writer. Re-run this table after a version bump —
the generated files carry no version marker, so nothing tells you it moved.

## Setup gotchas

- `onboard`, `setup`, `init`, and `init --global` can mutate `~/.bashrc`,
  `~/.zshrc`, or similar shell files.
- If user manages dotfiles separately, prefer manual MCP config, a manual eval
  snippet, or `lean-ctx init <shell> --style=dropin` — see "Which CLI forms are
  safe to run" below. NOT `init --global --style=dropin`, which installs.
- `AGENTS.md` can be regenerated by lean-ctx on startup; do not store durable
  local policy there.
- `setup` should not touch project rules unless opted in.
- Binary updates can require hook rewiring after swap.
- Editor MCP config reload may not refresh tool list; restart if uncertain.
- Avoid fixed host paths in reusable instructions.
- Rules-injection gating differs by client: `auto_inject_rules` controls
  OpenCode/Cursor/Codex (AGENTS.md), while Claude Code (CLAUDE.md) uses
  separate `rules_injection` + `rules_scope`. Disable the correct gate for
  your editor.
