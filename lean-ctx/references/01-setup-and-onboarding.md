# Setup and onboarding

## Mental model

Setup stages usually flow: wrap → onboard → setup → install → bootstrap → init.
Names differ by entrypoint, but intent stays stable: install binary, connect
shell/editor/MCP, generate safe guidance, and verify integrations.

## Fresh install

1. Install or update the `lean-ctx` binary using upstream-supported method.
2. Default to no environment mutation first: manual MCP config or
   `lean-ctx init --agent <tool>`.
3. Ask whether shell-hook or RC-file edits are also wanted before using
   onboarding/setup/global init flows.
4. Accept rules/instruction changes only when user explicitly wants them.
5. Restart or reload editor/MCP host if tool-list registration changed.
6. Run `lean-ctx status` and `lean-ctx doctor`.

## Onboarding outputs

- CLI and MCP availability checks.
- Optional shell hook edits.
- Optional editor MCP config snippets.
- Optional rules/instruction files.
- Backup files such as `*.lean-ctx.bak` before RC edits.

## Setup gotchas

- `onboard`, `setup`, `init`, and `init --global` can mutate `~/.bashrc`,
  `~/.zshrc`, or similar shell files.
- If user manages dotfiles separately, prefer manual MCP config, manual eval
  snippet, or `lean-ctx init --global --style=dropin`.
- `AGENTS.md` can be regenerated by lean-ctx on startup; do not store durable
  local policy there.
- `setup` should not touch project rules unless opted in.
- Binary updates can require hook rewiring after swap.
- Editor MCP config reload may not refresh tool list; restart if uncertain.
- Avoid fixed host paths in reusable instructions.
- Rules-injection gating differs by client: `auto_inject_rules` controls
  OpenCode/Cursor/Codex (AGENTS.md), while Claude Code (CLAUDE.md) uses
  separate `rules_injection` + `rules_scope`. Disable the correct gate for
  your editor.
