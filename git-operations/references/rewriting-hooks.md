# Hooks that rewrite files during a commit

Load this when a commit reported `files were modified by this hook`, when a
generated artifact is stale after a commit that succeeded, or when you must know
whether a hook's rewrite actually survived. Everything here is about `pre-commit`
(the framework) specifically — under `husky`, `lefthook` or bare `.git/hooks`
scripts none of it applies, because those runners do not stash, so the hook runs
against your dirty tree and its rewrite survives or fails on its own terms.

`SKILL.md` carries the part you need before committing: how to detect a real
install, and the obligation to verify the artifact by content afterwards. This
file is the evidence and the mechanism.

## Detecting the framework, and why `--git-path` is not a portable string

The detection command lives in `SKILL.md`. The measurement behind it, verified on
git 2.43.0 with pre-commit 4.6.2, 2026-08-26: the framework writes a banner into
the generated hook —

```text
# File generated by pre-commit: https://pre-commit.com
ARGS=(hook-impl --config=.pre-commit-config.yaml --hook-type=pre-commit)
```

— and matching that banner detected a real install while rejecting both a
hand-written hook and husky's. Matching the bare string `pre-commit` instead
false-positives on any hand-written hook that mentions it in a comment, which is
the ordinary way to write one.

**`--git-path` is absolute only from a linked worktree, or when `core.hooksPath`
is itself absolute.** Otherwise it is relative to the **current directory**.
Measured the same day, from two levels down:

| Configuration | `git rev-parse --git-path hooks/pre-commit` |
|---|---|
| Plain clone, from the root | `.git/hooks/pre-commit` |
| Plain clone, two levels down | `../../.git/hooks/pre-commit` |
| `core.hooksPath=.husky`, from the root | `.husky/pre-commit` |
| `core.hooksPath=.husky`, two levels down | `../../.husky/pre-commit` |
| `core.hooksPath=/abs/path` | `/abs/path/pre-commit` |
| Linked worktree | `/abs/path/to/main/.git/hooks/pre-commit` |

Husky sets `core.hooksPath` **relatively**, so the redirected case is exactly as
unsafe as the plain one. Never store the string and reuse it from elsewhere.

## The stash collision, and why the stage decides everything

pre-commit stashes unrelated unstaged work for the run. When a rewriting hook's
output collides with that stash on restore, the fix is thrown away:

```text
[WARNING] Stashed changes conflicted with hook auto-fixes... Rolling back fixes...
```

**What happens next depends entirely on the hook's stage.** Verified on git
2.43.0 with pre-commit 4.6.2, 2026-08-26:

- **pre-commit stage** — the hook reports `files were modified by this hook`, the
  commit **ABORTS** (exit 1), nothing is lost. Loud, and harmless.
- **post-commit stage** — the commit object already exists before the hook runs,
  so the commit **SUCCEEDS** (exit 0) while the rollback discards the rewrite.
  HEAD then carries a stale generated artifact and nothing in the output says so.

Only the second is dangerous, and a warning that does not name the stage reads as
though both were.

## `git status` is not the test

After committing into a dirty tree in a repo with a post-commit rewriting hook,
MUST verify the artifact by its **content**, or by whatever drift check it has of
its own. In the measured run `git status` showed the artifact modified — but
indistinguishably from the sibling lane's edit that caused the collision, so it
prompted no follow-up. It has also been observed showing the artifact clean. It
is uninformative in both directions, which is worse than being wrong in one.
